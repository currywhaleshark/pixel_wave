# 픽셀아트 제작 규격 — 픽셀 파도

이 문서는 **아트 제작자용 사양서**입니다. 코드 쪽 단일 진실 원천은 [`js/assets.js`](../js/assets.js)이며, 여기 표와 항상 일치해야 합니다.

## 1. 해상도 규격

| 항목 | 값 |
|---|---|
| 월드 해상도 | **480 × 270** |
| 화면 출력 | 정확히 **2배** 확대 (960 × 540), 보간 없음(nearest) |
| 게임 로직 좌표 | 960 × 540 (`CFG.pxUnit = 2` → 월드 픽셀 1 = 로직 2) |
| HUD·한글 텍스트 | **960 × 540 레이어에 별도 렌더** (확대되지 않아 또렷함) |

- 모든 스프라이트 좌표·크기는 **월드 픽셀(480×270 기준)** 로 표기합니다.
- 스프라이트는 그릴 때 자동으로 월드 픽셀 격자에 스냅됩니다(반픽셀 뭉개짐 방지).
- 320×180은 채택하지 않았습니다 — 적탄 반경이 월드 1.7px까지 줄어 탄막 가독성과 작은 피격판정 표현이 무너집니다. 480×270에서 적탄은 월드 약 2.5~3.5px로, 확대 후 5~7px이 되어 읽힙니다.

## 2. 시트 구성

| 시트 | 경로 | 내용 |
|---|---|---|
| main | `assets/sprites.png` | 플레이어·돌고래·잡몹·거북·탄·진주 |
| boss | `assets/bosses.png` | 보스 7종 |

- 투명 배경 PNG(RGBA).
- **프레임은 가로로 이어 붙입니다**: 프레임 i의 좌상단 = `(x + i*w, y)`.
- 파일이 없어도 게임은 정상 동작합니다(도형 폴백).

## 4. 색·톤 가이드

앨범아트 기준 — 픽셀 + 파스텔 바닷속 + 칩튠.

| 용도 | 색 |
|---|---|
| 인어 머리 | `#ff9ec7` |
| 인어 꼬리 | `#3fd8c7` |
| 진주 | `#ffffff` → `#e8d8ff` → `#b39ddb` |
| 큰 진주 | `#ffffff` → `#ffe9a8` → `#f2b64e` |
| 적탄(기포) | `#cfeaff` 테두리 + 반투명 속 |
| 적탄(가시) | `#ffffff` → `#ffb3cf` |
| 등불/기뢰 | `#ffd66e` |
| 별탄 | `#eafffb` / `#8ef0e2` |
| 유령 | `#d8f4ec` (반투명 25%↔90%) |

**탄막 가독성이 최우선입니다.** 적탄은 배경과 명도 차가 크게, 외곽 1px 밝은 테두리 권장. 배경은 채도를 낮춰 탄이 묻히지 않게.

플레이어 물결탄은 생성 바다 위에서도 읽히도록 스프라이트 바깥의 상하좌우에만 `#145a70` 1 월드 픽셀 외곽선을 55% 알파로 렌더합니다. 대각선까지 둘러싸는 진한 외곽선은 둥근 조개처럼 보이므로 사용하지 않습니다. 외곽선은 시각 효과일 뿐 탄 크기와 피격 판정을 바꾸지 않습니다.

### Pixel Wave 픽셀 규칙

1. 모든 게임 스프라이트는 최종 월드 해상도에서 1픽셀 단위로 제작한다.
2. 확대·축소된 가상 픽셀 블록을 사용하지 않는다.
3. 반투명 안티에일리어싱 픽셀을 사용하지 않는다. 알파는 `0` 또는 `255`만 허용한다.
4. 색은 해당 sprite run의 `palette.lock.json`에 잠긴 팔레트만 사용한다.
5. 1px 고립 픽셀은 눈·발광점 등 의도적 세부에만 허용한다.
6. 곡선은 직접 정리된 pixel stair-step cluster로 표현한다.
7. 애니메이션 프레임은 동일 재질에 동일 팔레트 인덱스를 유지한다.
8. 생성 원본의 제작 방식은 제한하지 않지만, 최종 `game_input`은 이 규격을 만족해야 한다.

자동 검사는 캔버스·프레임 크기, 이진 알파, 잠긴 팔레트 외 색, 투명 픽셀의 RGB 데이터, 빈 프레임, 고립 컴포넌트, 안전 여백, 인접 프레임 팔레트 분포 변화를 확인합니다. `sprite-request.json.pixel_lint`가 선언된 자산은 추출 피치 붕괴, 콘텐츠 종횡비, 프레임 간 콘텐츠 경계 변화도 강제합니다. 곡선의 계단 모양과 1px 세부의 의도는 자동 판정하지 않고 사람이 최종 확인합니다.

## 5. 작업 흐름 (생성 → 규격화 → 검증 → 패킹)

각 sprite-gen run은 생성·추출 결과인 `sprite-sheet-alpha.png`를 보존합니다. 게임에 들어가는 표준 입력은 이를 결정적으로 후처리한 `sprite-sheet-pixel.png`이며, manifest의 `game_input`이 이 파일을 가리킵니다.

```powershell
python tools/pixel_normalize.py --all
python tools/pixel_lint.py --all
python tools/build_sprite_sheets.py
```

`pixel_normalize.py`는 알파를 이진화하고 투명 픽셀 RGB를 비우며 잠긴 팔레트의 최근접 색으로 정규화합니다. 작은 연결 컴포넌트 삭제는 눈·발광점을 훼손할 수 있으므로 기본적으로 끄며, 필요한 run을 사람이 확인한 뒤 `--remove-isolated-max N`으로만 사용합니다. `pixel_lint.py`의 객관적 규격 위반은 실패하고, 고립 픽셀·안전 여백·프레임 팔레트 변화는 경고합니다. run별 보고서는 `pixel-normalize.report.json`과 `pixel-lint.report.json`, 전체 lint 요약은 `assets/generated/pixel-lint.report.json`에 기록됩니다.

패킹 후 점진 교체 절차:

1. 패킹된 `assets/sprites.png` 또는 `assets/bosses.png`에서 해당 칸과 애니메이션을 확인한다.
2. `js/assets.js`에서 그 항목의 `on: false` → **`on: true`**.
3. 새로고침 — 그 캐릭터만 스프라이트로 바뀌고 나머지는 도형 유지.

> `on` 플래그가 없으면 "시트는 로드됐지만 아직 안 그린 칸"이 **투명하게 그려져 적이 사라집니다.** 반드시 그린 항목만 켜세요.

### 배경 파이프라인

배경은 캐릭터 시트와 분리해 `AI concept → sprite-gen 모티프 행 → 투명 프레임 추출 → 3화면 연속 스트립 합성 → 코드 FX·패럴랙스`로 제작합니다. AI 원본을 그대로 축소한 이미지는 게임 입력으로 사용하지 않습니다.

- 바닷물 베이스는 별도 ImageGen 장경 원본에서 종횡비를 유지한 구간을 골라 `1440×270`으로 정규화합니다. 10색 수중 팔레트와 좌우 seam bridge를 적용한 완전 불투명 스트립이며 런타임 1배율로 매우 느리게 스크롤합니다.
- 생성 바다 위에 원경·중경·근경 암반과 코드 광선·부유 입자를 겹칩니다. 생성 원본에는 산호, 암반, 생물, 기포를 넣지 않아 레이어 역할이 섞이지 않게 합니다.

- 논리 화면은 항상 480×270이며 배경 패치도 이 격자에서 직접 제작합니다.
- 물색 밴드·빛줄기·기포·플랑크톤은 코드로, 산호·암벽·식생·랜드마크는 생성 모티프를 연속 암반에 구워 넣은 스트립으로 구성합니다.
- 원경·중경·근경은 각각 `1440×24`, `1440×36`, `1440×128`의 단일 PNG입니다. ImageGen 장경 원본을 화면 한 장 폭인 480 월드 픽셀 패널로 정규화하고, 이음새가 맞는 패널 3개를 이어 구성합니다. 근경의 기본 암반은 약 36px 높이를 유지하되, 처음부터 하나의 연결된 실루엣으로 생성·추출한 89px·113px 대형 암반 덩어리를 드문드문 둡니다. 작은 패치를 확대하거나 여러 패치를 쌓아 대형 덩어리를 만들지 않습니다. 128px 캔버스의 윗부분은 이 덩어리를 위한 투명 여유입니다. 런타임 배율은 항상 1이며 세로만 누르거나 임의 배율로 다시 그리는 것은 금지합니다.
- 스트립의 첫 열과 마지막 열은 완전히 동일해야 하며, 각 레이어는 하나의 연결된 불투명 지형 바닥을 가집니다.
- 원경·중경·근경 패널 경계 `0/480/960px`에는 각 깊이에 맞는 `sprite-gen` 암반 seam cap을 1:1로 겹쳐 이음매를 가립니다. cap 자체를 확대·축소하지 않습니다.
- 근경은 게임 화면에서 알파 `1.0`으로 그려 뒤 레이어가 비치지 않게 합니다. 원경·중경만 깊이감을 위한 낮은 불투명도를 허용합니다.
- 경계 사이에는 높이 26~32px의 작은 암반과 44~47px의 대형 암반을 번갈아 배치해 능선 높이를 불규칙하게 만듭니다. 모든 덩어리는 추출 프레임을 1:1로 사용합니다.
- 원경·중경·근경 패럴랙스 속도는 각각 `0.14`, `0.38`, `0.82`입니다.
- 디더링은 넓은 무늬가 이동하며 지글거리지 않도록 경계 전환에만 제한적으로 사용합니다.
- 플레이 영역 중앙은 저채도·낮은 대비로 유지하고 장식 밀도는 위·아래 가장자리에 집중합니다.

1스테이지 생성 모티프는 `assets/generated/backgrounds/stage1-coral-patches/`, 연속 스트립 manifest·팔레트·lint 결과는 `assets/generated/backgrounds/stage1-coral-strips/`에 보존합니다. 최종 게임 입력은 `assets/backgrounds/stage1-{far,mid,near}-strip.png` 세 장입니다.

2스테이지 **해파리 초원**은 보랏빛 저녁 바다와 세 겹의 연속 초원 스트립으로 구성합니다. 원경·중경·근경 캔버스는 각각 `1440×48`, `1440×72`, `1440×128`이며 실제 실루엣 높이 범위는 `6~39px`, `11~62px`, `24~124px`입니다. 한 높이의 리본처럼 이어 붙이지 않고 낮은 공터, 중간 융기, 2배·3배 높이의 큰 단일 랜드마크 사이에 긴 호흡 구간을 둡니다.

- 세 지형 소스는 세로로 눌러 맞추지 않고 종횡비를 보존해 화면 한 장 폭 `480px`로 정규화합니다.
- 패널 경계 `0/480/960px`마다 해당 레이어 원본의 식생 밀집부에서 잘라낸 작은 초원 seam cap을 1:1로 덮습니다. cap 양끝은 1px 높이까지 가늘어져 별도의 수직 절단면을 만들지 않습니다.
- 근경은 완전 불투명, 원경·중경은 저대비 반투명으로 그려 적과 탄을 가리지 않습니다.
- 생성 원본·잠금 팔레트·cap·manifest·lint 보고서는 `assets/generated/backgrounds/stage2-jelly-meadow/`에 보존합니다. 최종 입력은 `assets/backgrounds/stage2-{sea,far,mid,near}-strip.png`입니다.

3스테이지 **거북이 고속도로**는 쨍한 청록 해류 띠를 차선처럼 사용하고, 유선형 암초·자연 아치·뒤로 휜 부채산호로 속도를 표현합니다. 문자 표지판이나 아스팔트 같은 육상 도로 기호는 사용하지 않습니다.

- 최종 캔버스는 바다 `1440×270`, 원경 `1440×56`, 중경 `1440×72`, 근경 `1440×128`입니다.
- 원경·중경·근경은 모두 한 덩어리로 이어지며, 패널 경계는 생성 지형 표면에서 추출한 바닥 연결형 seam cap으로 덮습니다.
- 근경은 긴 낮은 구간 사이에 2~3배 높이의 넓은 아치형 능선을 두되 플레이 영역 중앙의 적·탄 실루엣은 가리지 않게 합니다.
- 바닷물은 수평 해류 클러스터와 사선 광선만 포함하고 지형·생물·기포는 별도 레이어와 코드 FX가 담당합니다.

## 7. 픽셀 폰트

현재 텍스트는 전부 `Fonts.f()`를 거칩니다([`js/fonts.js`](../js/fonts.js)). 폰트 파일이 없으면 **sans-serif로 자동 폴백**하므로, 파일을 넣는 순간 전 화면이 한 번에 바뀝니다.

### 배치

```
assets/fonts/Galmuri9.woff2   (+ .ttf)
assets/fonts/Galmuri11.woff2  (+ .ttf)
```

`index.html`의 `@font-face` 이름과 `js/fonts.js`의 `faces[].family`가 일치해야 합니다.

### 왜 크기가 다른 폰트를 둘 이상 두는가

비트맵 계열 픽셀 폰트는 **고유 크기의 정수 배**로만 또렷합니다(11px 폰트를 13px로 그리면 뭉개짐).
하나만 쓰면 11·13·16px이 전부 11px로 뭉쳐 **위계가 사라집니다.** 9px + 11px 두 개를 두면:

| 요청 | 실제 | | 요청 | 실제 |
|---|---|---|---|---|
| 11 | 11 (11×1) | | 22 | 22 (11×2) |
| 13 | 11 | | 30 | 33 (11×3) |
| 16 | 18 (9×2) | | 36 | 36 (9×4) |
| 20 | 22 | | 44 | 44 (11×4) |

`Fonts.f()`가 로드된 페이스 중 요청에 가장 가까운 조합을 자동으로 고릅니다. **합성 볼드는 쓰지 않습니다**(픽셀 폰트에 가짜 볼드를 씌우면 획이 뭉개짐) — 강조는 색과 크기로.

### 폰트 후보 (한글 지원)

| 폰트 | 고유 크기 | 라이선스 | 비고 |
|---|---|---|---|
| **갈무리 (Galmuri)** | 7 / 9 / 11 / 14 | OFL | 픽셀 게임용으로 설계, 한글·일문·라틴 폭넓음. 현재 코드의 기본 가정 |
| **둥근모꼴 / Neo둥근모** | 16 | OFL | 한국 도트 게임의 고전. 16px 고유라 HUD엔 다소 큼 |
| **Dung Geun Mo** | 16 | 개인·상업 무료 | 위와 동계열 |

> 다른 폰트를 쓰려면 `js/fonts.js`의 `faces` 배열(패밀리명·고유 크기)과 `index.html`의 `@font-face`만 바꾸면 됩니다.

### 적용 폰트 (2026-08-27)

**갈무리(Galmuri) 2.40.3, OFL-1.1** — `assets/fonts/`에 Galmuri9 / Galmuri11 / Galmuri11-Bold(woff2, 합계 ~1.1MB) + `OFL.txt`.
Galmuri11에는 **진짜 볼드**가 있어 합성 볼드 없이 강조가 됩니다(`Fonts.f(px, true)`).

### 텍스트를 어느 레이어에 그릴 것인가 — 실측 결론

캔버스 `fillText`는 **픽셀 폰트에도 안티에일리어싱을 적용**합니다(측정: 11px에서 AA 픽셀 비율이 sans-serif와 동일한 수준). 이걸 피하려고 두 가지를 시험했습니다.

| 시도 | 결과 |
|---|---|
| 비트맵 내장 TTF (`Galmuri11Bitmap`) | **렌더 불가** — 아웃라인이 없어 캔버스에서 아무것도 안 그려짐(0픽셀). 폐기 |
| 월드 레이어(480)에 11px → 2배 확대 | **더 뭉개짐** — 11px의 AA가 2×2 블록으로 증폭 |
| **960 레이어에 22px (고유의 2배)** | **가장 또렷** — 채택 |

즉 **텍스트는 960 레이어에 고유 크기의 2배 이상으로** 그리는 현재 방식이 맞습니다. 픽셀 폰트를 native 크기(11px)로 그리는 것은 오히려 손해입니다. `Fonts.f()`가 요청 크기를 배수로 스냅하므로 호출부는 신경 쓸 필요가 없습니다.

### 화면 맞춤 (정수 배율)

픽셀아트는 비정수 배율로 늘리면 픽셀이 뭉개집니다. `fitCanvas()`가 뷰포트에 맞는 **480×270의 정수 배**로만 표시 크기를 정합니다(1280×800 → 960×540 = 정확히 2배). 화면이 480×270보다 작을 때만 소수 배율로 축소합니다.
